Key points

What this project covers and found, in brief.

  • A framework that turns one prompt into a working product through role-chartered agent sessions with shared JSON state.
  • Every build is logged and curated in its own run-log dashboard, the Codex: 14 logged builds, 13 assessed.
  • 9 of 13 first deliveries worked without a re-prompt. No plain-session baseline yet.
  • Builds include an MLB daily dashboard and an Apple Music now-playing Stream Dock plugin.

The question

Can one plain-language prompt (“build me an app to play blackjack”) turn into a working product with no follow-up, if the work is split across specialised agents that check each other? AutoBuilder is the architecture I built to find out. Each build is a measurement of that architecture, not a product to polish.

From sketch to roles

It started as a hand drawing: discovery, technical discovery, then sections with an overseer and builders each. Nothing in that drawing doubts the work, so before the first run the design grew roles whose only job is to check the others: a long-running Critic, an Arbiter that routes problems by severity, a Historian that keeps the decisions, and a Convergence Verifier that tests the finished product against the original spec.

How a build runs

Every role writes to its own files, and only the owner of a file may write it, so each decision leaves a record. After delivery, each build gets a second, user-side label: did the person who typed the prompt get something that worked on first contact? That outcome is the number this page leads with. It is kept apart from the pipeline’s own verdict, because the two disagreed more than once. A dashboard (the codex) reads the run files and draws each build’s topology.

What changed, and what it cost

Each failure became an amendment, and the failed prompt was re-run word for word afterwards. I didn’t patch failed builds: a patched build hides the failure the architecture needs to learn from.

v1.3 · Gave up trusting each section’s own tests → gained acceptance assertions per section and a required run of the integrated product in a browser-like sandbox. Trigger: a blackjack button that never re-enabled.

v1.5 · Gave up testing against a simulated browser with dependencies swapped in → gained a production-fidelity check: the verifier opens the deliverable the way the user will. Cost: an earlier pass was reclassified as a failure.

v1.7 · Gave up a growing list of per-artifact test rules → gained one property to check: every claim in a spec has at least one test pointing back at it.

v1.9 · Gave up trusting the model’s familiarity with outside products → gained four principles: a product named in the prompt is a specific external system, every load-bearing claim about it needs a citation, success is verified at the level it is claimed, and the verifier may not share the builder’s source of truth. Trigger: a plugin built for macOS, delivered to a Windows user.

Throughout · Gave up repairing builds that failed → gained clean before-and-after comparisons on the same prompt.

Failure modes

  • MLB dashboard (v1.10.1): the install steps didn't work as written and the dashboard itself didn't satisfy the request; fixed by iterating in the same chat
  • Blackjack (version not recorded): the Deal button stayed disabled after a hand ended, past every gate; Jett found it
  • LaTeX renderer (v1.4): passed AutoBuilder's verifier, but the math library never loaded in a real browser
  • Stream Dock plugin (v1.8): passed every gate, but was built for macOS; Jett is on Windows

Limits

  • No baseline: nobody ran the same prompts in a single agent session, so this shows what AutoBuilder delivered, not that it beat anything
  • Small sample: 13 builds. The Wilson 95% interval is wide (42% to 87%)
  • Mixed versions: the 13 builds span architecture v1.3 to v1.10.1 (4 record none), and the architecture changed after almost every failure, so this is not one system measured 13 times and not a trend
  • Partly self-labelled: 3 of the 9 successes are 'with concerns' from the uncertainty-manifest rule alone, without Jett's ratification; 5 labels were set by the Codex or Maintenance instance in curation files
  • Narrow prompt mix: 12 of the 14 runs are browser apps (tic-tac-toe, kanban, blackjack and the like); the one prompt outside the browser, a hardware plugin, failed on its first attempt

Outcome: Partly. Goal: one prompt in, a working product out, with no follow-up. 9 of 13 assessed first deliveries met it, 4 needed a re-prompt, and there is no baseline yet to say whether that beats a plain agent session. Paused since May 2026, not retired: I may return to it.

How I used AI

What the tools did, and what was checked.

Tools
Claude Desktop Cowork agent sessions: one chat per build, running AutoBuilder's role charters as sub-agents. Two long-lived Cowork instances: Codex (run-log dashboard and curation) and Maintenance (architecture amendments, per-build git).
Models
Not recorded per run.
Extent
Agents wrote every build, its run report and its verification, and the codex dashboard and aggregator. The architecture amendments were drafted by agents in conversation with Jett. Jett sketched the first architecture by hand and set the direction of each change.
My role
Spec and evaluation design: chose the prompts, defined the user-side first-delivery outcome as the measure, tested delivered builds himself, ratified finished builds and had the final say on amendments, including re-running failed prompts verbatim instead of patching builds.
What checking caught
  • The LaTeX renderer passed AutoBuilder's own verifier, then showed 'library not loaded' for every input the first time Jett opened it. The verifier had tested in a simulated browser with the library installed locally. Fix: v1.5 requires testing the deliverable the way the user opens it.
  • The Stream Dock plugin passed every internal gate but was built for macOS; Jett is on Windows, and the build had Windows paths in front of it. Fix: v1.9 adds principles that treat a named product as a specific outside system and require a citation for every load-bearing claim about it.
  • A re-audit reclassified the first blackjack build from 'pass with concerns' to failed, so the run log doesn't keep a misleading green flag.
  • While building this page: the codex index labels the Stream Dock A/B pair the wrong way round (the v1.9 run is tagged as the first attempt). The page orders the pair by architecture version and date; the run log is left as it is.
